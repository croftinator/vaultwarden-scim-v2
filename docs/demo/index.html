Vaultwarden SCIM + SSO demo

Fifteen minutes, entirely local. One identity provider handles both sign-in and provisioning - the same shape as Microsoft Entra in a real deployment.

Before you start. Run tools/scim-demo.sh and wait for Ready. Open four things: the web vault (https://localhost:8000), Authentik (http://localhost:9000), Mailpit (http://localhost:8025), and a database client pointed at 127.0.0.1:15433. You also need a second browser profile for step 7 - one browser cannot hold two Bitwarden sessions, and Ada signs in there while you stay signed in as the Owner.
If you are ever unsure what to do, run this: 
tools/scim-demo.sh --next
It inspects the live state and prints the single next action, with the exact credentials for it. It also repairs anything recoverable first - a stray account from an accidental SSO sign-in, or a member left half-onboarded - so it can never tell you to do something that cannot work.

The steps below are the narrated version of the same sequence. You do not need to follow them in order: --next derives the order from where you actually are, which is what makes wrong turns recoverable rather than terminal.

What you are looking at

PieceRole
VaultwardenThe password manager. This fork, PostgreSQL-backed.
AuthentikThe identity provider. Pushes users in over SCIM, authenticates over OIDC.
MailpitCatches every email, so invites work with fictional addresses.

The directory contains five people. Four are in Engineering and are synced. One, Charles Babbage, is a Contractor and is deliberately not - proving SCIM syncs what it is scoped to and leaves the rest alone.

The walkthrough

  1. Web vault

    Sign in as the Owner with a master password.

    owner@example.com / demo-master-password-1

    The starting point: an ordinary encrypted vault, no SSO involved yet.

  2. Web vault

    Look at the vault items and the Example Corp organization.

    Real encrypted data, written by a real client. None of it could have been inserted with SQL - the server never holds the key that would let it.

  3. Web vault

    Note the Enterprise single sign-on button, but stay signed in as the Owner.

    The Owner exists only in Vaultwarden and has no Authentik identity, so SSO cannot authenticate them - somebody has to hold the organization key before anyone can be provisioned, and that person cannot themselves come from the directory. SSO is demonstrated at step 7, as Ada, who does come from the directory.

    The email you type is ignored by the SSO button. Vaultwarden redirects to Authentik and lets Authentik decide who you are - so if you already have an Authentik session in that browser (from opening its admin UI at step 4, say), you are silently signed in as that identity, with no prompt. Typing owner@example.com and clicking SSO signs you in as akadmin and creates a stray admin@example.com account in Vaultwarden.

    Two consequences worth planning around: keep the Authentik admin UI in a different browser profile from the one you demo in, and if you do end up with a stray account, tools/scim-demo.sh --reset clears it.
  4. Authentik

    Open Directory → Users and Groups.

    One directory owns identity. Engineering has four members; Contractors has one who will never appear in Vaultwarden.

  5. Terminal

    Force a provisioning cycle.

    tools/scim-demo.sh --sync

    Authentik otherwise syncs on its own schedule. The commonest reason a demo looks broken is impatience, not breakage.

  6. Web vault → Admin Console → Members

    Four new members. Every one of them says Invited.

    This is the honest part of the demo, and the most important. SCIM created the accounts and the memberships, and then stopped. It cannot go further, and neither can any amount of server-side code.

    SELECT u.email, uo.status, LEFT(uo.akey, 24) AS akey
FROM users_organizations uo JOIN users u ON u.uuid = uo.user_uuid
ORDER BY u.email;

    status = 0, and akey is empty.

  7. Mailpit + second browser profile

    Open Mailpit, find Join Example Corp addressed to ada.lovelace@example.com, and click the link. Set her master password to demo-master-password-2.

    One step does two things: it creates her account, deriving a master key in her browser, and it joins her to the organization. Her status becomes Accepted (1) - she has an account, but still no organization key.

    Do this before showing SSO, not after. The invite link carries the real organization identifier, so post_set_password runs accept_org_invite and the join completes (src/api/core/accounts.rs:481).

    Sign in via SSO first and you get stuck: SSO sends FAKE_SSO_IDENTIFIER (src/sso.rs:20) instead, so the join is skipped and only the account is created. The invite link then shows the same "set a master password" form, which the server refuses with "Account already initialized" - because private_key already exists (accounts.rs:443). Recovering means logging in as Ada first, then re-opening the link.
  8. Second browser profile

    Now log Ada out and sign back in with Enterprise single sign-on: ada.lovelace / demo-sso-password-2 at Authentik.

    This is the steady state a real employee lives in. Two credentials doing two different jobs: the Authentik password proves she is Ada, the master password derives her vault key in the browser. The server sees neither.

    This profile must have no existing Authentik session, or you are signed in as whoever it already holds without being asked. No Authentik login prompt means exactly that - sign out of Authentik here and retry.
  9. Web vault, as Owner

    Confirm Ada.

    Watch what just happened: your browser fetched Ada's public key, encrypted the organization's symmetric key under it, and sent the result. The server stored a blob it cannot read. status = 2 and akey is now populated.

    This step is why the demo installs real clients. There is no server-side path that can produce a valid akey, so "fully automatic provisioning" is not a feature anyone can honestly ship on an end-to-end encrypted vault. What is automated is everything either side of it.
  10. Authentik

    Deactivate Ada Lovelace - the member you just confirmed - then tools/scim-demo.sh --sync.

    The offboarding path, and the highest-value one: it needs no keys, so it is fully automatic and immediate.

    Deprovision the member you confirmed, not one who is merely Invited. An Invited member has an empty akey, so the next step's "the key survived" observation would be true of a row that never held one - green, and proving nothing. Katherine stays Invited on purpose, as the contrast: revoking her gives -128 rather than -126.
  11. Database

    Check what deactivation actually did.

    SELECT u.email, uo.status, LEFT(uo.akey, 24) AS akey
FROM users_organizations uo JOIN users u ON u.uuid = uo.user_uuid
WHERE u.email LIKE 'ada%';

    The row is still there, status is -126, and akey is byte-for-byte what it was before - compare it against what you saw in step 8. Revocation is an offset of 128 applied to the previous status, not a distinct value - so a revoked-confirmed member reads -126.

    StateStored
    Invited0
    Accepted1
    Confirmed2
    Revoked-invited-128
    Revoked-confirmed-126
    MembershipStatus::Revoked = -1 is a comparison sentinel that is never stored. Code testing status == -1 is wrong for every real row; test status <= -1.
  12. Authentik

    Reactivate Ada and sync again.

    She returns to Confirmed, not Invited. Nobody re-confirms her, because her wrapped key was never destroyed. A returning employee is restored, not re-onboarded - which is the difference between revocation and deletion, and the reason this design keeps the row.

  13. Desktop app / browser extension

    Unlock the same account in another client.

    Same vault, same organization, same membership state. Set the server to https://localhost:8000 before logging in - it cannot be changed afterwards.

If something looks stuck

SymptomCause
Members do not appearAuthentik syncs on a schedule. Run tools/scim-demo.sh --sync.
A client rejects the certificateRun mkcert -install, then restart the client - it reads the trust store at startup.
The desktop app refuses the URLIt requires HTTPS with no localhost exemption. Use https://.
bw rejects the certificateNode ignores the system trust store: export NODE_EXTRA_CA_CERTS="$(mkcert -CAROOT)/rootCA.pem"
Everything is confusedtools/scim-demo.sh --reset returns to the seeded state without a rebuild.
